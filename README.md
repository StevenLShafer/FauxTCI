# FauxTCI

FauxTCI is a simulated target-controlled infusion (TCI) syringe pump and its
controller, running entirely in the browser as a static page: no server, no
framework, no build step, no dependencies. You set the pump's maximum rate and
its other limits, pick propofol or remifentanil, enter an effect-site (or
plasma) target, and watch the pump run in real time or faster: the loading
infusion, the pause until the effect site peaks, the hand-off to a slowly
falling maintenance rate, and what happens on a hand bolus, a pause, a lost
response or a wrong syringe. The left-hand panel is a running transcript of
every request the pump sends to the controller and every response it gets
back, because the point of FauxTCI is to show how a pump talks to the
[stanpumpR TCI API](https://github.com/StevenLShafer/stanpumpR/blob/master/docs/tci-api.md).

## What the controller is, and is not

The controller inside the page is a **JavaScript reimplementation** of the
stanpumpR TCI API (`R/tci-api.R`, `R/tci.R`): the same request body in, the
same response body out, the same algorithm (Shafer and Gregg 1992, as in
`tciRate()`), the same two drug models (Eleveld 2018 for propofol; Eleveld
2017 below a BMI of 30 and Kim 2017 at or above it for remifentanil), the
same validation, error codes and warnings. It is **validated against
fixtures generated by the R package** (see [How it was validated](#how-it-was-validated)),
and the page says so. **It is not the R service.** Nothing in this
repository runs R.

The page can also talk to a real `stanpumpR::run_tci_api()` server. In
Setup, set Controller to "HTTP: a stanpumpR server" and enter the server's
URL; the page then POSTs each request to `<URL>/tci/v1/drugs/<drug>/rate`
and applies the response under the same safety contract. Two things to know:

* **CORS.** A browser only lets the page call a server that allows the
  page's origin. `run_tci_api()` sends no CORS headers (the API's deployment
  guidance, section 7.1 of the contract, is CORS disabled on a controller
  path), so for a teaching demonstration put a reverse proxy in front of the
  server that adds `Access-Control-Allow-Origin` for the page's origin and
  answers the `OPTIONS` preflight (`Access-Control-Allow-Methods: POST, GET,
  OPTIONS`, `Access-Control-Allow-Headers: Content-Type`), or add an
  equivalent Plumber filter to `tciApiRouter()` in a development session.
  Never on a production ingress.
* **Clocks.** The server reports `CLOCK_SKEW` when its own clock and the
  request's `now` differ by more than 30 s. The page's simulated clock starts
  at the wall clock, so at 1x the two agree; at 5x, 10x or 60x the simulated
  clock runs ahead and every response from a real server carries the warning
  (the computation is unaffected: the server uses the request's clock).

## Run it locally

The page is plain HTML, CSS and ES modules, so any static file server will
do; opening `index.html` from `file://` does **not** work, because browsers
refuse to load ES modules from `file:` origins.

```sh
git clone https://github.com/StevenLShafer/FauxTCI.git
cd FauxTCI
npx http-server . -p 8080 -c-1      # or: python3 -m http.server 8080
```

then open http://localhost:8080/ . There is nothing to install and nothing
to build.

## The page

* **Setup**: drug, patient (weight, height, age, sex), syringe concentration
  (propofol 10 or 20 mg/mL; remifentanil 20, 50 or 100 mcg/mL), the pump's
  maximum rate (1200 mL/hr), minimum rate (0.1), resolution (0.1), syringe
  volume (50 mL), the declared latency (1.5 s), the actual latency (1.5 s),
  the interval (10 s), the clock multiplier (1x, 5x, 10x, 60x) and the
  controller (in page, or HTTP with a URL). Start begins a case; Stop sets
  the target to 0, ends the case and halts the clock.
* **Target**: effect site or plasma, in the drug's units, with the typical
  range; a target of 0 stops the infusion.
* **Pump face**: the rate in mL/hr with the mass rate beneath, the status
  lamp and phase (loading, waiting for peak, maintenance, above target,
  stopped, paused, ALARM), the segment's hold countdown and its fallback
  rate, the next-request countdown, the syringe volume remaining and the
  time to empty, the case clock.
* **Charts**: effect-site concentration, true (solid) and as predicted by the
  controller (dashed), the target, and the true plasma concentration
  (lighter); beneath, the pump rate as a step line with the maximum rate
  dotted. Minutes of case time; propofol yellow and remifentanil blue as in
  stanpumpR.
* **Delivery record**: the pump's record as a table, with "Copy as JSON" and
  "Download as stanpumpR dose table (CSV)" (Drug, Time in minutes, Dose,
  Units: `mg` or `mcg` boluses, rate rows in `mg/hr` or `mcg/min`), which
  the stanpumpR app can load to plot the same case.
* **Wire details**: the last request and response as JSON, with the status,
  the transport in use and a one-line log of every exchange.
* **API conversation** (left on a wide screen, below the pump face on a
  narrow one): one card per exchange with the request and response bodies,
  a one-line reading of each response, its warnings or errors, and when it
  was sent, received and applied to the pump. "Summaries only / Full JSON",
  "Copy conversation", "Clear" and a Follow toggle.

### What the teaching controls demonstrate

* **Hand bolus**: drug given outside the pump. The record gets a `bolus`
  event, the controller answers with the pump off (phase "above target")
  and gives nothing until the effect site has fallen back to the target.
* **Pause / Resume**: a paused pump reports `pump.state: paused` and rate 0;
  the server still plans (warning `PUMP_NOT_RUNNING`), projecting the
  latency at rate 0, and the pump decides not to run the plan. Resume asks
  at once and the next response restarts the infusion.
* **Drop next response**: the next response is lost in transit. The pump
  runs its segment to `holdUntil`, then the response's fallback rate; had no
  later command been accepted it would have stopped and alarmed (section 7,
  rule 4 of the contract). A response dropped during loading shows that the
  fallback is itself a safe plan: under a cap it is another capped partial
  interval (504.1 mL/hr for the default propofol case), and once loading is
  complete it is 0 (off until the peak); either way the peak never exceeds
  the target.
* **Change syringe**: the controller is told one concentration while the
  syringe really holds another. The true and predicted curves diverge and
  `DELIVERY_MISMATCH` appears; the controller can only be as right as its
  record.
* **Actual latency**: how long the simulated pump really takes to
  acknowledge a command, against the declared `timing.latency`. Slower than
  declared, the loading rate runs too long and the effect site overshoots
  (section 5.5: about 10% for 3.0 s against a declared 1.5 s under a
  1200 mL/hr cap); longer than the interval, no response is ever applied in
  time, the fallback expires and the pump alarms.
* **A hidden tab**: the controller sleeps while the tab is in the
  background. On return the pump has done what the contract says a pump
  does without its controller: it ran its segment to `holdUntil`, the
  fallback for `maxSeconds`, then stopped and alarmed. A new target restarts
  it.
* **Clock**: 1x is a real case; 60x shows a 30-minute case in 30 s. The
  request bodies carry the simulated clock, which is why they stay
  consistent at any speed.

## How it was validated

The fixtures in `test/fixtures/` were generated from stanpumpR at commit
`740b5055f12c9616cac4fec869ab2b6d1b3b777a` (version 0.0.1.9002, R 4.3.3,
jsonlite 1.8.8) by `test/fixtures/generate.R`; `test/fixtures/README.md`
describes each file and the tolerances a port should aim for. The suite
(`node --test 'test/*.js'`, Node 22, about five seconds) replays them; the
figures below are the worst cases the tests print as TAP diagnostics:

| Fixture | What is checked | Tolerance | Achieved (worst case) |
|---|---|---|---|
| `models.json` (2 drugs x 8 patients) | PK parameters, eigenvalues, every bolus and infusion coefficient, with R's ke0 injected | 1e-10 relative | 3.9e-14 (parameters and eigenvalues), 5.4e-13 (coefficients) |
| `ke0-solve.json` | ke0 from tPeak by the same nested Brent fmin as R (tol 2^-13 at both levels) | 1e-6 relative aimed, 2.5e-4 hard bound | 1.7e-11 from the covariates; 1.0e-11 from the fixture's own inputs; inner peak time within 5.8e-12 min; the effect site after a unit bolus peaks within 2.6e-5 min of tPeak (tolerance 0.01 min) |
| `rate-cases.json` (49 success cases) | every numeric field of the response with R's ke0 injected | 1e-8 relative | 2.3e-10 (`rate.ideal`); every other field at or below 4.2e-11 |
| `rate-cases.json`, the port's own ke0 | the same, with ke0 solved in JavaScript | 1e-8 relative | 3.6e-7 relative on `rate.ideal` (9.8e-9 mL/hr absolute, at a pump-off step where the ideal rate is a residual of the effect-site search; the commanded rates match exactly); `state.now.e[]` 1.4e-10; the state and prediction concentrations at or below 1.2e-11 |
| `rate-cases.json`, strings | `rate.value` after rounding, `limitedBy`, `controller`, every timing string, `peakAt`, `targetReachedAt`, warning codes and pointers | exact | exact |
| `rate-cases.json` (13 error cases) | status, code and pointer | exact | 12 exact; `DUPLICATE_KEY` is skipped with a note (`JSON.parse()` keeps only the last copy of a duplicated key, so the body cannot be refused after parsing) |
| `model.hash` | MD5 of the parameters rounded to ten significant digits, in jsonlite's spelling | format | the value equals R's in 65 of 65 model blocks |
| `closed-loop.json` (6 traces x 181 steps) | the commanded rate, fallback rate, plan, phase, every timing string, warning codes, the server's state at `now`, the true Cp and Ce at every step, the recorded history and the trace's maximum true Ce | rates 1e-8, concentrations 1e-6 relative; strings exact | `rate.value` 2.2e-16, `fallback.rate` 1.7e-16, `state.now.ce` 1.2e-11, `prediction.peakCe` 5.6e-12, true Ce 1.3e-11, maximum true Ce 5.6e-12, recorded rates exact; the pump's own running maximum, sampled at its tick instants rather than on the fixture's 1 s grid, is within 5.7e-6 of the fixture's (trace 5, the 300 mL/hr cap) |

Beyond the fixtures, `test/pk.test.js` checks `advance()` against a
Runge-Kutta integration of the compartment equations (1.5e-13 relative),
`test/tci.test.js` exercises every error and warning code and the
section 7 rules, and `test/pump.test.js` drives the pump through a dropped
response, a pause, a lowered target, a wrong syringe, a background gap, a
late or crossed response, a three-hour compaction and the dose-table export.
`test/smoke.playwright.js` opens the page in Chromium (when Playwright is
installed), runs a propofol case at 60x to maintenance, gives a hand bolus,
checks for console and page errors and for horizontal overflow at 375 px,
and writes `test-results/smoke.png`; without Playwright it skips.

Run the suite with Node 22:

```sh
npm test                    # = node test/run.js
node --test "test/*.js"     # the same files, through node --test directly
```

`test/run.js` names the files itself through node:test's `run()`, so `npm
test` needs no shell glob. (Node 22 takes glob patterns, not directories, so
`node --test test/` does not work; the quotes keep the pattern from the
shell.) Playwright for the smoke test: `npm install -g playwright && npx
playwright install chromium`.

### Regenerating the fixtures

From a stanpumpR checkout at the commit above:

```sh
cd /path/to/stanpumpR
LC_ALL=C.UTF-8 NOT_CRAN=true RENV_CONFIG_AUTOLOADER_ENABLED=FALSE \
  Rscript /path/to/FauxTCI/test/fixtures/generate.R /path/to/FauxTCI/test/fixtures
```

The run takes about 20 s, ends with a validation pass that replays every
request through `tciNextRate()`, and writes `manifest.json`. `tciNextRate()`
is deterministic, so a regeneration differs only in `generatedAt` and the
`server.*` blocks, which the tests do not compare.

## Layout of the repository

```
index.html              the page (markup only)
css/fauxtci.css         styles, light and dark
js/pk.js                the drug models, eigenvalues, coefficients, ke0, closed-form advance
js/tci.js               the API port: tciNextRate(request) -> response, tciApiDrugs(), tciApiModel()
js/pump.js              the simulated pump and its controller (the section 7 safety contract)
js/transport.js         in-page or HTTP transport
js/app.js               the page: wiring, charts, tables, the API conversation panel, the clock
js/md5.js               MD5 for model.hash
test/run.js             the runner behind npm test (node:test's run() over the files below)
test/*.test.js          node:test conformance and behavioural tests
test/smoke.playwright.js   the browser smoke test
test/fixtures/          the stanpumpR golden fixtures and their generator
.github/workflows/      test.yml (push, pull request) and pages.yml (deploy to Pages)
```

## Clinical disclaimer

FauxTCI is a teaching simulation. It is not a medical device, it has not
been evaluated by any regulator, and nothing in it is to be used for patient
care, for programming a real pump, or for any clinical decision. The drug
models are population models from the literature; an individual patient's
concentrations differ from them.
